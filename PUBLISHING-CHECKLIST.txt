FEXAFY — PUBLISHING / RELEASE CHECKLIST
=========================================
Practical notes for the four technical items below. Nothing here
changes the app itself except where noted (crash reporting and the
update mechanism are already wired into index.html/sw.js — see
README.txt "WHAT'S NEW IN THIS VERSION (v13/v14)").

1) APP SIGNING KEY
-------------------
This only applies if/when you wrap this PWA as a native Android
APK/AAB (e.g. with Capacitor, Trusted Web Activity, or Bubblewrap) to
publish on the Play Store — a plain website/PWA install has no
signing key of its own. IMPORTANT: I can't generate this key for you.
It has to be created on your own machine, tied to your own Play
Console app listing, and it is genuinely irreplaceable:

- If you lose it (or the keystore password), you CANNOT publish
  updates to the same app listing ever again — Google will not
  transfer or reset it for you. Your only options at that point are
  publishing under a brand-new listing (losing all reviews/installs)
  or, if you're enrolled in Play App Signing, in some cases requesting
  Google's help via their key-reset support flow (not always possible,
  and not guaranteed).
- Generate it with Android's own `keytool` (ships with any JDK), e.g.:
    keytool -genkey -v -keystore fexafy-release.keystore -alias fexafy -keyalg RSA -keysize 2048 -validity 10000
- Use Google Play App Signing (Google keeps a copy of your app signing
  key securely and re-signs for distribution) — this is the default
  and recommended path for new apps, and gives you a safety net if
  your local upload key is ever lost (you can request a reset of just
  the "upload key" in that case, which is NOT possible for the app
  signing key itself if you opt out of Play App Signing).
- Back up the .keystore file AND its password in at least two
  independent places you control (e.g. a password manager entry with
  the file attached, plus an encrypted offline backup) — never only on
  the one machine that built it, and never in this project's git repo
  or any public/shared location.

2) CRASH REPORTING
-------------------
Already added in v13 (see README.txt). Two layers, both offline by
default:
- A local-only error log (last 20 errors), viewable/downloadable from
  Account & Backup -> Diagnostics. Never leaves the device.
- An optional Sentry hook, off by default. To turn it on: get a free
  DSN from https://sentry.io, paste it into the `SENTRY_DSN` constant
  near the top of the main <script> in index.html, and — since this
  does start sending crash data (device/browser info, stack traces —
  never your financial figures) to a third party — update
  privacy-policy.html section 4 to name Sentry, the same way the other
  third-party services are already documented there.

3) VERSION / UPDATE MECHANISM
-------------------------------
Already improved in v13 (see README.txt). To ship a new version:
bump the single `APP_VERSION` constant at the top of sw.js — the
cache name and cleanup follow automatically. Installed users now also
see an in-app "A new version is ready — Refresh" banner the next time
they open the app after you deploy an update, instead of silently
running old cached code until they happen to reload.

4) PERFORMANCE WITH LARGE DATASETS (500+ TRANSACTIONS)
---------------------------------------------------------
Tested with synthetic datasets of 500 / 2,000 / 5,000 transactions
against the app's actual filtering/aggregation logic (Node.js,
V8 engine — see method note below):
- This month's dashboard view (filter + categorize + render): well
  under 25ms even at 5,000 total transactions.
- Full-history search/filter (Account -> Search & filter): 2–20ms to
  filter and sort, even at 5,000 transactions.
None of that showed a real slowdown. Two safety margins were still
added, since raw JS filtering speed isn't the only cost on a real,
possibly low-end phone:
- The search text box now waits ~180ms after you stop typing before
  re-filtering (previously it re-filtered on every single keystroke).
- Search results are capped at rendering the first 300 matching rows
  at once (with a note if there are more), so a very broad search
  over thousands of transactions can't paint thousands of DOM rows in
  one go — the filtering/count itself still covers your full history.

  Method note / honest limits: these numbers measure the JavaScript
  logic itself (array filtering, sorting, categorizing) in Node, which
  is what actually scales with transaction count. Real on-device
  screen-painting time (DOM rendering) could not be measured here — 
  that requires an actual browser, which isn't available in this
  sandboxed environment. The two safety margins above (debounce + a
  render cap) directly target that gap. If you want real device
  numbers before publishing, the practical way is: Restore a backup
  with 500+ entries (or add them via a quick script against
  localStorage) on an actual mid-range phone and scroll/search/type
  in Transactions and Search & filter — watch for dropped frames.
