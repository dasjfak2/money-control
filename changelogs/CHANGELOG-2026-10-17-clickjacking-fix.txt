FEXAFY — FRONTEND: REAL CLICKJACKING PROTECTION (CSP meta tag was a no-op for this)
=====================================================================
Files: index.html (v102 -> v103). sw.js bumped to v103 too, to stay in
sync (no other change in sw.js). check.js/register.js: untouched.

THE FINDING (confirmed against the real file, not just in theory)
The CSP <meta> tag in <head> has always included `frame-ancestors 'none'`,
intended as clickjacking protection (stop this app from being loaded
inside someone else's <iframe>). It never actually worked: per the CSP
spec, `frame-ancestors` (along with `sandbox` and `report-uri`/`report-to`)
can ONLY be delivered via a real HTTP response header — a
`<meta http-equiv="Content-Security-Policy">` tag is specifically
required to ignore it. Confirmed directly: loading the real file in a
real browser prints this exact warning to the console:
  "The Content Security Policy directive 'frame-ancestors' is ignored
   when delivered via a <meta> element."
Since this app is hosted on GitHub Pages (static hosting, no custom HTTP
headers possible), there was never a way to make that directive actually
take effect — it's been silently doing nothing since it was added.

WHAT CHANGED
Added a small inline <script> right at the very top of <head> (before
every other tag except charset/viewport/theme-color) that does the real
job: if the page is ever loaded inside a frame on a different origin, it
navigates the TOP window away to this same page, breaking out of the
frame before a user could be shown anything clickable inside it.

  try {
    if (window.top !== window.self) {
      window.top.location.replace(window.self.location.href);
    }
  } catch (e) { /* nothing more to do from inside the frame */ }

This runs synchronously, before anything renders, and is a complete no-op
in every normal case (opened directly, bookmarked, installed as a PWA) —
window.top === window.self then, so the check does nothing at all.

The frame-ancestors 'none' entry in the CSP meta tag was left in place
(for documentation, and as a safety net for any future hosting that DOES
deliver this over a real header), but both CSP comments in the file were
corrected to stop overclaiming what it actually does today.

DISCLOSED LIMITATION (same honesty standard as the other security
changelogs in this project)
A frame using the HTML `sandbox` attribute without `allow-top-navigation`
can block even this script's attempt to navigate away, silently, with
nothing the script can do about it from inside the frame. This is a
narrow, deliberate attack setup, not the common case — and there's no way
to close that specific gap from pure static hosting; doing so would mean
serving a real `X-Frame-Options`/`Content-Security-Policy` HTTP header,
which means hosting this file somewhere that supports custom headers
(e.g. Vercel — which already hosts the push backend — or Netlify/
Cloudflare Pages) instead of GitHub Pages. Not changed here since you're
currently on GitHub Pages by choice; worth keeping in mind if that ever
changes.
