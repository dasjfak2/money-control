1) THE BUG — new installs showed a "safe spending" amount on Home
   before the person had entered anything
--------------------------------------------------------------------
CONFIRMED ROOT CAUSE: a brand-new account's db.setup object starts
with suggested starter numbers (income ৳50,000, invest ৳5,000, savings
৳5,000, emergency-monthly ৳2,000, etc.) — these exist only so the
Budget Setup form isn't blank the first time someone opens it. A
separate flag, db.setup.configured, is already tracked precisely to
tell "real, saved budget" apart from "still just the starter
suggestions" — it flips to true only when Budget Setup is actually
saved (saveSetup()).

The Home page's hero card, however, computed and displayed "safe
spending money" straight from db.setup's numbers regardless of that
flag. So a new install — configured:false, zero transactions — showed
roughly ৳38,000 "safe to spend" (৳50,000 starter income minus starter
invest/savings/emergency shortfalls), which is exactly the wrong-
amount-on-first-install behaviour reported.

Notably: the fix for this was already half-built. The HTML already
had a `#heroEmptyState` block ("Set up your budget" / "Add your
monthly income and savings goals…" / a "Set up now" button routing to
Budget Setup), fully styled in CSS, with English + Bengali text
already in the translation dictionary — it just had `class="hidden"`
hard-coded on it with nothing in the JS ever toggling it. It was
built and then never wired up.

THE FIX: `updateHeroCard()` now checks db.setup.configured before
computing/showing anything:
  - Not yet configured (new installs, or any account that hasn't
    saved Budget Setup): shows the existing "Set up your budget"
    empty state and a "Set up now" button straight to Budget Setup;
    hides the status pill too (an "On track"/"Spend carefully" pill
    would be equally meaningless before real numbers exist). No
    number is computed or shown at all.
  - Configured: unchanged — the same real-time calculation and hero
    card as before, computed from actual income/spending/goals.
Existing users who already had data before this update are unaffected
— the app already infers configured=true for anyone with existing
transactions, bills, debts, recurring items, future goals, assets, or
a filled-in profile (see migrateDb()), so this only changes what a
genuinely fresh, empty account sees.

ONE INCONSISTENCY FOUND AND FIXED — Sentry vs. the CSP:
Your SENTRY_DSN constant already has a real DSN in it (crash
reporting genuinely turned on, apparently from a previous session),
and Privacy Policy section 4 already correctly discloses this. But
the Content-Security-Policy added in the last security pass never
included Sentry's script domain (browser.sentry-cdn.com) or its
ingest domain — meaning the browser was silently blocking Sentry's
script from loading at all. Net effect: crash reports have not
actually been reaching Sentry, even though your code and your Privacy
Policy both say they should be. This was a gap, not a safety feature
— I closed it by adding those two exact domains to script-src /
connect-src (nothing broader). If you'd rather crash reporting stay
fully off for now, just blank out SENTRY_DSN near the top of the main
<script> — the CSP entries are harmless either way when it's empty.
